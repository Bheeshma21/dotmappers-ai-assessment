# AI Support Ticket Analyst

An AI-powered support ticket analytics system built for the DotMappers AI Intern Assessment.

The application allows users to ask natural-language questions about support ticket data, performs safe data analysis using Pandas, detects anomalous tickets, exposes REST API endpoints using FastAPI, and provides an interactive Streamlit interface.

## Features

- Natural-language querying of support ticket data
- LLM-powered query interpretation using Groq
- Safe structured query execution using Pandas
- Statistical and rule-based anomaly detection
- FastAPI REST API
- Streamlit web interface
- CSV data validation and preprocessing
- Automated tests with Pytest
- API key protection using environment variables

## Architecture

```text
User
  |
  v
Streamlit UI
  |
  v
FastAPI REST API
  |
  v
LLM Engine
  |
  +---------------------+
  |                     |
  v                     v
Query Engine       Groq LLM
  |
  v
Validated JSON Query Plan
  |
  v
Pandas Data Analysis
  |
  v
support_tickets.csv
```

The LLM does not execute arbitrary Python code.

Instead, the system converts the user's natural-language question into a structured JSON query plan. The query plan is validated against allowed operations and columns before Pandas executes it against the CSV dataset.

The calculated result is then passed to the LLM to generate a clear natural-language response.

## Natural-Language Querying

The application supports questions such as:

```text
How many Billing tickets are Open?
```

```text
Which agents have the highest average resolution time?
```

```text
What is the average customer rating for Technical tickets?
```

```text
Show me all Critical tickets with resolution time greater than 12 hours.
```

The LLM translates the question into a restricted JSON query plan.

Example:

```json
{
  "operation": "count",
  "target_column": null,
  "filters": [
    {
      "column": "priority",
      "operator": "eq",
      "value": "Critical"
    },
    {
      "column": "status",
      "operator": "eq",
      "value": "Escalated"
    }
  ],
  "group_by": null,
  "sort": "desc",
  "limit": 10
}
```

Pandas then performs the actual filtering, grouping, and calculations.

This design reduces hallucination risk because numerical results come from the dataset rather than being generated by the LLM.

## Supported Query Operations

The query engine supports:

- count
- average
- sum
- minimum
- maximum
- list/filter operations
- grouping
- sorting
- multiple filters

Supported filter operators include:

- equal
- not equal
- greater than
- greater than or equal
- less than
- less than or equal

## Anomaly Detection

The project combines statistical anomaly detection with business rules.

### Statistical Detection

The Interquartile Range (IQR) method is used to detect unusually high:

- response times
- resolution times

The upper threshold is calculated using:

```text
Q3 + 1.5 * IQR
```

For the supplied dataset:

```text
Response time threshold: 7.65 hours
Resolution time threshold: 48.15 hours
```

### Additional Business Rules

Tickets are also flagged when:

- customer rating is 2 or lower
- High or Critical priority tickets remain unresolved and have a response time greater than 4 hours

With the current rules, 79 of the 500 supplied tickets are flagged as anomalies.

## REST API

Start the FastAPI backend with:

```bash

```

```text

```

### Endpoints

#### Health Check

```http
GET /health
```

Returns the API status and number of loaded tickets.

#### Dataset Summary

```http
GET /summary
```

Returns overall support ticket statistics.

#### Ask AI

```http
POST /ask
```

Example request:

```json
{
  "question": "How many Billing tickets are Open?"
}
```

Example response:

```json
{
  "question": "How many Billing tickets are Open?",

}
```

```http
GET /anomalies
```

Returns the anomaly summary and detected anomalous tickets.

## Security

The application follows several safety practices:

- API keys are loaded from environment variables
- `.env` is excluded from Git
- the LLM cannot execute arbitrary Python
- generated query plans are validated
- only approved dataset columns can be queried
- only approved query operations and filter operators are executed

## Limitations

- Natural-language interpretation depends on the LLM correctly mapping a question to the supported query-plan schema.
- The query engine intentionally supports a restricted set of operations for safety.
- The application requires a valid Groq API key for AI-powered querying.
- The current implementation is designed specifically for the supplied support-ticket schema.
